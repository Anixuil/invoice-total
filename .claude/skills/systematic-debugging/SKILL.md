# 系统化调试

## 原则

先用证据定位根因，再做最小修复。不要通过叠加补丁掩盖症状。

明显的局部错误可以走快速路径：直接读取报错位置及其直接引用，确认因果关系后修复，不必展开完整调查。

## 调试流程

1. **界定现象**
   - 记录实际行为、期望行为、错误信息和触发条件。
   - 判断问题能否稳定复现；不能复现时先收集更多证据。

2. **追踪根因**
   - 从错误值或异常状态向上追踪数据来源。
   - 对比同仓库中正常工作的相似实现。
   - 多组件链路只检查边界输入、输出、配置和状态传递。

3. **提出单一假设**
   - 明确说明“X 是根因，因为 Y”。
   - 只用一个最小变化或静态证据检验该假设。
   - 假设不成立时回到证据，不在失败补丁上继续叠加。

4. **实施最小修复**
   - 在根因产生处修复，不在下游吞掉错误。
   - 不捆绑无关重构或顺手优化。
   - 只有用户明确要求时才添加或运行测试、构建、lint 或类型检查。

5. **静态 Review**
   - 重读本次 diff 和直接引用。
   - 确认修复能解释原始现象，并覆盖明显边界情况。
   - 检查是否引入新的共享状态、竞态或失效值。

## 升级条件

连续三次假设或修复失败时停止局部补丁，重新评估架构、共享状态和组件边界，并向用户说明证据与阻塞点。

## 按需参考

- 深层调用栈的数据来源：读取 `root-cause-tracing.md`。
- 异步等待或竞态：读取 `condition-based-waiting.md`。
- 根因修复后的分层防御：读取 `defense-in-depth.md`。

## 禁止

- 未说明根因就直接尝试修复。
- 同时修改多个变量来“看看是否有效”。
- 因无法复现而猜测原因。
- 在用户未要求时运行验证命令。
